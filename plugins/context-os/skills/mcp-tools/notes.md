# Notes, Bases, Records, and Links

## Notes

- **Create with `note_create`.** The path must end in `.md`. The server supplies standard frontmatter defaults (a title derived from the file name unless you give one, timestamps, and an `entity` derived from where the note sits) and you add the rest through `frontmatter` (`type`, `tags`, and so on). The `entity` is the configured entity whose top-level directory holds the note, and `vault` anywhere else, `memory/` included (a folder named for an entity below the first path segment, such as `memory/tasks/<entity>/`, does not count); a vault with no `.contextos/entities.toml` gets no `entity`, and a malformed one refuses the note (`format/entities`). Pass `entity` yourself for any note outside a top-level entity folder that belongs to an entity, since the location cannot tell. The `type` default stays `note`: set `type` through `frontmatter` for any other kind. `base_record_create` derives a record's `entity` the same way. It only creates: it never overwrites, so an existing path is refused. Use it in place of `fs_write_file` with hand-built YAML.
- **Copy a file into a note with `content_from`, not by reading and rewriting it.** Give `note_create` a `content_from` of `{path, expected_hash?}` in place of `content` and the server copies that vault file's body in verbatim: the content never passes through you, costs no tokens, and cannot be altered on the way. This is how a source is filed into `memory/raw/`. A Markdown source's (`.md`, in any case) frontmatter is left behind, because the note's properties come from your `frontmatter` and the defaults; read any you want to keep with `frontmatter_read` (it skips the body) and pass them on. Any other text file (a `.txt` transcript, say) is copied whole. Pass the `content_hash` from your last read as `expected_hash` so a source changed since is refused (`io/conflict`, naming the source) rather than copied unseen. `content` and `content_from` together, or neither, is `io/invalid-argument`; a binary source is `io/binary`; a source over the read limit is `io/too-large`; and the result's `content_hash` is the written note's. `references` still work and follow the copied body.
- **Cite with `references`.** Each entry is a `target` (a note name or path without brackets) and a one-line `summary`. The tool appends a `# References` section of `[[target]]: summary` lines, so you do not format citations yourself.
- **Read properties with `frontmatter_read`,** which returns the ordered frontmatter and the hash without the body.
- **Change properties with `frontmatter_update`,** which applies a JSON merge patch (RFC 7386) and preserves the body.
  - A key you set replaces the old value, and a key set to `null` is deleted.
  - Nested objects merge key by key.
  - An array replaces the whole array. To add one tag you must send the full list, so read first, or use a tool built for that field (see [Links](#links-between-records)).
  - `updated` is stamped for you unless the patch sets it.
  - The whole frontmatter block is written back from its parsed form. YAML comments are lost, quoting and flow style (`[a, b]`) are normalised, and blank alignment is dropped. For a hand-annotated note, change the one line with `fs_edit_file` instead.
  - The current hash is checked automatically against the file as it is at call time. Supply `expected_hash` only to guard against changes since your own earlier read.
- **Change the body with `fs_edit_file`** (see [files.md](files.md)) when the edit is a few exact lines.
- **Change properties and body together with `note_update`,** never `frontmatter_update` followed by a body write: two writes can leave the fields saved and the body refused.
  - Give `patch` (the same merge patch as `frontmatter_update`), `body` (everything after the frontmatter's closing `---` line), or both. `expected_hash` is required.
  - `created` is kept and `updated` is stamped. A patch naming either is refused with `format/note-managed-field`.
  - The title rules of `note_create` hold for any title, description, summary, or excerpt the patch changes (`format/note`), and the body is checked as Obsidian Markdown (`format/markdown`).
  - Like `frontmatter_update`, it writes the frontmatter block back from its parsed form even for a body-only change, so YAML comments are lost. For a hand-annotated note, change the body with `fs_edit_file` instead.
  - The returned `content_hash` is the note as written; use it for the next write.

## Bases

A `.base` file is a view definition: filters, formulas, properties, and views over notes. It stores no data, and the records are ordinary notes. A keyed Base has a paired sidecar `<name>.md` that hands out ids.

- **Change a definition** by calling `base_read` (it returns the definition, schema diagnostics, and the hash), then one `base_apply` with `expected_hash` and every operation in order. The whole result is validated before anything is written, and it applies atomically or not at all, so put all your edits in one call.
- **Create a Base** with `base_create`, and end its top-level `filters` with `&& file.basename != "index"` so a folder's managed `index.md` is never one of its records. Ids are unique within the folder those filters name (`file.inFolder(...)`, or `file.folder ==` for only the notes directly in it), `index` notes aside, whatever else they say: `base_record_create`'s id and `unique_fields` checks and `doctor` all use that scope, so a `status` condition hides records from views without freeing their ids. Filters that name no folder make the Base the notes they select. Declare its id series up front with `key_prefix` (the default series) and `key_prefixes` (further series, for example `A` for actions and `D` for decisions). Supply neither for a Base that needs no ids, which is keyed by file path.
- **Leave the sidecar to the server.** It holds the counters, so do not edit them by hand and do not work out the next id yourself.
- **Declare what a series is, by hand.** A sidecar can name the template each series follows and the fields it fixes: `template` (one link, which binds every series), `series_templates` (a link per declared prefix, overriding `template` for that series), and `fixed_fields` (names of fields beyond `type`, which is always fixed, that the template fixes). Only literal template values can be fixed: a placeholder, a Templater expression, a menu such as `a|b`, an empty value, a list, or a map cannot. The server reads these keys and never writes them, so add them by hand with `fs_edit_file`; a single `template` serving series of different kinds (an action, a decision, a question) is wrong, so give each kind its own `series_templates` entry.
- **Query a Base** with `base_query`, giving either an existing `path` plus an optional `view`, or an inline `definition` with a `vault`. Choose `json` for data you will process and `table` for something to show. Only a subset of the Bases grammar evaluates: `==`, `!=`, `.contains()`, `.containsAny(...)`, `.containsAll(...)`, `file.hasTag()`, `file.inFolder()`, and `&&`, `||`, `!`, and parentheses. Anything else is refused before any note is read, naming the construct. A formula column shows its value only when it is a bare property reference or `file.asLink()`, and any other formula shows an unevaluated marker. A filter or sort key cannot use `formula.*`. Scope with `file.inFolder("...")` rather than comparing `file.folder`, because it lets the scan narrow to the folder.
- **Fetch records by id** with `base_query` and `ids` (1 to 100) plus the Base's `path`, not a view. Each record comes back with its `path`, `frontmatter`, and `content_hash`, and its body too with `include_content: true`; ids nothing holds are listed in `not_found`. This is the cheapest way to read a known record, or every task a `depends_on` list names, in one call instead of a query and a read for each. Do not pass `view`, `limit`, or `format` with `ids`.

## Records in a keyed Base

Create a record with `base_record_create`, never with `note_create` and a guessed id.

- The server assigns the id from the sidecar and advances that series' counter, so two records cannot receive the same id. **Do not put `id` in `frontmatter`** for a keyed Base, because it is refused. Read the assigned id from the result's `key`.
- `prefix` picks the series (`D` for a decision beside a default `A`). It is case-sensitive and must be declared in the sidecar, or the call is refused with `io/invalid-key-prefix`. Omit it to use the default series.
- `folder` is relative to the folder the Base's own filters name (`file.inFolder("...")` or `file.folder == "..."`, which `base_read` reports as `records_folder`). A leading `/` makes it relative to the vault root instead, and a Base whose filters name no folder requires it. A `file.folder ==` Base holds only the notes directly in its folder, so it refuses a relative `folder`: omit it.
- `filename` defaults to the lower-cased key with a `.md` extension. Leave it to that default in a keyed Base: a record's file is named for its key alone, with no slug, so a vault decision, a vault question, and a task are `vd-003.md`, `vq-001.md`, and `a-071.md`. A Base with no id scheme (keyed by file path) requires you to give one, and a caller-supplied `id` is then accepted.
- **Omit `type` and the template's other fixed fields.** When the sidecar declares a template for the series, the record is stamped with that template's fixed fields instead of `type: note`, so do not guess a `type`. A value you supply that equals the template's is kept; one that differs is refused with `io/fixed-field-conflict`, whose `fields`, `series`, and `template` members say what clashed and which series to use instead (the value is never echoed): omit the field, or create the record under the series that fixes the value you want. A template that cannot be used (not found, ambiguous, not Markdown, too large, malformed, without a literal value for a fixed field, or a base's sidecar rather than a template) is refused with `format/series-template`, naming the link and the reason; nothing is written and no id is spent, so tell the operator to fix the template or the sidecar rather than retrying or working around it with `note_create`. A Base declaring no template still writes `type: note`.
- The new note is stamped with a `base` link naming its Base. Supply it only if it is the same Base. A bare `[[decisions.base]]` written by hand resolves to the nearest `decisions.base` in the note's folder or an ancestor, as any link does, so it is safe inside a project tree that has its own.
- The call is refused rather than reusing an id already held by a note in the Base's scope, and nothing is written when a call is refused before writing, which covers an undeclared prefix, an invalid argument, and an id collision.
- One failure is different. The id is reserved in the sidecar before the note is written, so a note that then cannot be written fails with `io/key-reserved-note-not-written` and leaves a gap in the series. Do not create the record again under a guessed id: retry the creation, which takes the next id, or tell the operator.
- **Reference a record by its key, never its path.** Wherever you mention a task or other keyed record, in a note, a link field, a journal entry, or an event, write `[[a-071|A-071]]`. A record can be moved to another folder (`fs_move_file`, or the task screen's Move), and a key link survives that where a path link breaks. Moving a task keeps its key and its file name.
- **Raising a record that may already exist.** When something may raise the same record more than once (a workflow rerun, a recurring check), give the record an identifying field such as `origin` and pass `unique_fields: ["origin"]`. A record already holding that value is refused with `io/duplicate-record`, whose `path` and message name it and its id: carry on with that record rather than creating another. Do not search first and create if absent, because two runs can both get past the search; `unique_fields` is checked inside the vault's write lock, so it holds across processes.
- **Claiming a record** (taking a task before working it): fetch it with `base_query` `ids`, check it is unclaimed or its claim has lapsed, then `frontmatter_update` it with the fetched `content_hash` as `expected_hash`. If another session claimed it first you get `io/conflict`: leave that task and move on.
- If the catalogue also lists a `base_record` tool with more actions than creation, read its schema and prefer it for updating and deleting records. Until then, change a record like any note.

## Events

Events are short notes under `memory/events/` that say what happened: a task changed state, a member went blocked, a job failed, a scheduled session started. They bring ContextOS Web to life and mark anything stopping clean operation in amber or red. They are not a second operation log, so do not record one for a tool call.

- **The server fires its own kinds.** Task changes (created, state changed, reassigned, claim lapsed, unknown state, moved), member state changes from `agent_state_change`, and vault health (a secondary service failing, then recovering) are written by the server as the call that causes them completes. No client records them, and you never need to after a claim, a state change, or a warning. The server writes them under the vault's write lock, so each is recorded once across every process.
- **Record a kind the vault declares.** Whatever knows a thing happened, such as a scheduled run or a job's data load, records it with `base_record_create` against `memory/events.base`, for a kind defined in the vault's `registry/events/`. Read that folder for the kinds that exist and their fields; this skill does not list them. Give `kind`, and as the kind allows, `severity` (`info`, `warning`, or `error`; the kind's default applies if you omit it), `subject` (one link to the note the event is about), `entity`, `content` (a short note for the body), and the kind's own fields at the top level. Never give `at`, a path or `filename`, `type`, `subject_id`, `subject_path`, `subject_base`, or the kind's key field: the server stamps them. Do not supply `title`, `created`, `updated`, `tags`, `aliases`, or `description`; events carry none of them.
- **Name a record by its key.** A task, or any record of a keyed base, is always referenced by its key, never its path: `subject: "[[a-071|A-071]]"`. When the record's file is not named for its key, link its file name labelled with its key (`[[ship-it|A-071]]`). Linking a record by its path is refused, and so is a subject that is not one whole wikilink or that names more than one note. The server stamps the record's key, base, and current path from the note the link names, so an event about a task stays about that task wherever it is filed. A link that names no note is kept with nothing stamped, so check that it names the note you mean. Any other note is linked by its path.
- **Moving a task fires `task.moved`,** naming where it was and where it is now, one per task when a folder of tasks moves. A move clears no warning about the task.
- **A key the kind assigns.** A kind that starts something others refer to names a key field, and the server assigns the next key under the write lock and returns it as the result's `key`. Pass `prefix` naming the series the events sidecar maps to that kind in `series_kinds` (the seeded `session.run-started` kind uses `S`); `prefix` is required for such a kind and refused for one without a key field. Take that key and use it; two sessions starting at once receive different keys, which a clock-made id cannot guarantee.
- **A recorder that may run again** passes `unique_fields` naming the field that identifies the event, as for any record. A repeat is refused with `io/duplicate-record`, naming the event already recorded: carry on with it.
- **An event is never edited,** and `memory/events/` is written only by the routes above: the server's own firing and `base_record_create` on `memory/events.base`, which is the only way a client records an event. Every other write, edit, move, or delete there is refused with `events/server-owned`, and so is moving or deleting `memory/events` itself or a folder that holds it, such as `memory`. To correct a mistake, record a new event.
- **Refusals write nothing and spend no key.** Read the code and act on its remediation:

| Code | Meaning |
| --- | --- |
| `events/unknown-kind` | `kind` is missing, or no usable definition in `registry/events/` declares it. Check the name, or ask the operator to add or fix the definition (`doctor` reports a definition it cannot use) |
| `events/server-fired-kind` | The server fires this kind itself. Do not record it |
| `events/invalid-severity` | The severity is not one the kind allows |
| `events/invalid-fields` | A required field is missing, or a field is neither declared by the kind nor one the request may carry, including a common note field |
| `events/invalid-subject` | A subject was given for a kind with none, is missing for a kind that requires one, is not one whole wikilink, names a record by its path rather than its key, or names more than one note |
| `events/invalid-series` | `prefix` is missing for a kind with a key field, was given for a kind without one, or names a series the sidecar does not map to this kind in `series_kinds` |
| `events/server-stamped` | The request supplied `at`, a path, a `filename`, a `folder`, `subject_id`, `subject_path`, `subject_base`, or the kind's key field |
| `events/server-owned` | A write, edit, move, or delete under `memory/events/` was attempted outside those routes |
| `packages/server-owned` | A write, edit, move, delete, or restore reached `.contextos/packages/`, the vault's installed package store (or a folder that holds it, such as `.contextos`). Only contextos-web writes there: install or remove releases with its workflows, libraries, and packages commands. The rest of `.contextos/` and `registry/` stay writable. Workflow code changes by editing its source under `registry/workflows/` and installing it with `contextos-web`, and a saved job file's `version` and `predecessor` change only through `contextos-web jobs successor` |

- **`events/write-failed` is a warning,** not a refusal. A call that caused a server-fired event succeeded, but the event could not be written. The call stands: do not retry it, and tell the operator.
- **Never decide what to work on from events.** Read the task records (`base_query` on `memory/tasks.base`) for what is actionable. Events say what happened and may be absent, swept after their retention window, or missing for a change made outside the server. A scheduled session that must work out what is left reads the tasks.

## Links between records

Cross-reference fields such as `depends_on`, `blocks`, `related`, and `parent` are declared by the Base under `link_fields` in its sidecar. Change them only with `frontmatter_link`.

- Pass `operations` of `add` or `remove` (1 to 100 per call), each with a declared `field` and a `target`. The target is the record's id for a record in the same Base (the value `base_record_create` returned as `key`), or a vault path (a leading `/` is the vault root). Put every link change for a note in one call. All operations are validated and then written atomically.
- The server checks the target exists, writes the link in its short form, and writes the reciprocal on the linked note when the field declares an inverse (`depends_on` and `blocks`, or a field such as `related` that is its own inverse). It is idempotent: adding a link that is present, or removing one that is absent, does nothing, so repeating a call is safe and repairs a reciprocal that failed.
- Do not write these wikilinks by hand, and do not use `frontmatter_update` on a link field. That replaces the whole array, skips validation, and skips the reciprocal.
- Do not rewrite existing links into a different form. Every form matches on later calls.
- Read the result. `changes[].outcome` is `added`, `already-present`, `removed`, or `absent`. `reciprocal[]` reports each linked note's `path`, `field`, `outcome`, and whether it was `written`, where the outcome can also be `skipped` (the linked note's Base does not declare the pair, which is silent). A reciprocal that could not be written is listed in `warnings`, and repeating the call fixes it once the cause is cleared.
- Errors name the fix. `link/undeclared-field` lists the fields the Base declares, `link/target-not-found` and `link/target-ambiguous` mean the id or path needs correcting (pass the vault path if an id is ambiguous), `link/single-valued` means a single-valued field such as `parent` is already set, and `link/no-link-fields` means the governing Base declares none.
- `expected_hash` is checked even when the note would not change, so a stale hash is refused with `io/conflict` and nothing is written, reciprocals included.

## Canvas and diagrams

- `canvas_read` returns nodes and edges with diagnostics. `canvas_apply` applies ordered operations atomically after validating the complete result, so read first and batch your edits into one call. `canvas_create` generates identifiers you omit.
- `mermaid_validate` checks a diagram taken from a note's fenced or inline source without rendering it. Validate first and render with `mermaid_render` (SVG) only once it passes.
