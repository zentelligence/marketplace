# Files: Reading and Writing

## Reading

**Whole text file: `fs_attach_file`.** It returns the complete file as one embedded resource in a single call, up to 10 MiB, and works for text and binary files alike (binary content arrives as a base64 blob with a detected media type). A text block after the resource carries the file's `content_hash`, taken from the exact bytes returned, and its `size` and `version`, so you can overwrite the file without another read. An older server omits that block, and [Getting the hash](#getting-the-hash) covers the fallback.

**A note with its links resolved: `fs_attach_file` with `expand_links`.** For Markdown notes (`.md`) and canvases (`.canvas`) only, and any other file is rejected. Every link in the body and in the frontmatter is rewritten in place to the vault-rooted path it names (`/` followed by a vault path), so you do not search for each link's target yourself. `[[Foo]]` becomes `[[/wiki/Foo.md|Foo]]`, an embed keeps its size hint, and a standard link `[text](Foo.md)` keeps its text and gains only the folder prefix, as does a reference definition `[id]: Foo.md`. A link that names no file becomes `/:!` followed by its original text (`[[/:!typo|typo]]`), and one that names several files becomes `/:?` followed by its original text. External URLs, `mailto:`, and anchor-only links are left as written. Links resolve from the note's own folder up through each ancestor to the vault root, nearest first, and then by file name across the whole vault, so an image or a note stored anywhere is found by name, and a name that matches several files is ambiguous unless exactly one of them is in the records folder of the base the note names in its `base` property. A file created since the server last looked is found on the next expansion. A canvas comes back as JSON with each text node's links expanded and each file node's `file` rooted or marked; a canvas that is not valid JSON Canvas is refused (`format/canvas-schema`). A note with more than 10,000 distinct link targets is refused (`format/too-many-links`). The text block after the resource reports `links_expanded` and carries no `content_hash`, because this is not the file's content. **Never edit or write back from expanded content.** Read the plain file with `fs_attach_file` before changing it.

**Why not `fs_read_text_file` for a whole file.** When the content a read would return reaches the server's inline threshold (5 KB unless the operator changed `resource_link_threshold_kb`), the result is cut to a bounded preview, `truncated` is set, and a resource link to the rest is attached. A host that supports resources can follow the link, and a host that does not is left with the preview. This applies to any slice too: a `head`, `tail`, or `range` result of 5 KB or more is previewed as well. Paging through a large file therefore costs one call per page and still risks truncated pages. A whole-file read above the vault's `max_read_mb` (5 MB by default) is refused outright unless you pass `head`, `tail`, `range`, or read the file in parts. `fs_read_multiple_files` previews the same way, so a `truncated` item is not the whole file: attach it with `fs_attach_file`.

**Part of a file: `fs_read_text_file`.** Use it when you genuinely want a slice: the tail of a log (`tail`), the opening of a large file (`head`), or a known section (`range` with inclusive `from_line` and `to_line`). Keep the slice small enough to stay under the threshold. Its `content_hash` always describes the complete file, whatever slice you asked for.

**A file too large to attach, a single very long line, or a host without resource links: parts.** `fs_read_text_file` with `offset` (default 0) and `length` (default and maximum: the inline threshold, minimum 4) reads a byte part by seeking, so it costs the part and never the file, and it ends on a whole character. Every read returns `size` and an opaque `version`. Read part 0, keep its `version`, then pass it as `expected_version` with each returned `next_offset` as the next `offset`, and stop when `next_offset` is `-1`. A part is `truncated` unless it is the whole file, and it has no resource link, since you continue by offset. If the file changed, the read fails with `io/conflict` and `current_version`: start again from the beginning. `offset` and `length` cannot be combined with `head`, `tail`, or `range`. A part carries no `content_hash` and no `line_count`, so never write from parts alone: re-read the whole file (`fs_attach_file`) to get its hash before you change it. `expected_version` is accepted on every `fs_read_text_file` selection, not only parts, and a stale one is reported as `io/conflict` before a bad `offset` or too-short `length` is reported (the `offset` or `length` with `head`, `tail`, or `range` refusal is an argument error and comes first). A part that holds a NUL byte or invalid UTF-8 is `io/binary`, and a read in parts always advances or fails, so the loop cannot spin. The `version` is a cheap guard on size, modification time, and identity (plus the change time on Unix), not proof of identical content: on Windows a same-size change that keeps the modification time can go unnoticed, and on Unix only a change that also leaves the change time alone could. Only a whole read's `content_hash` compares content exactly.

**Several files.**
- Small files: `fs_read_multiple_files`. One failing path does not fail the batch, so check each item's `error`. The batch size is capped (50 files by default), and a file at or above the threshold is previewed and flagged `truncated`.
- Large files: issue one `fs_attach_file` call per file, together in one response.

**Do not read to inspect.**
- Existence, kind, size, timestamps, or the current hash: `fs_get_file_info`. It returns a hash without content for any file within the read limit.
- A note's properties: `frontmatter_read` returns the ordered frontmatter and the hash without the body. With `expand_links: true` every link value (`base`, `parent`, `depends_on`, and so on) comes back resolved to its vault-rooted path by the same nearest-first rule as `fs_attach_file`'s `expand_links`, and no hash: read the values, never write them back.
- A note's links: `links_read`, whose `direction` is `out` (the default), `in`, or `both`. `out` and `both` return `outgoing` (each with `target`, `form`, `embed`, and `resolved`, the vault file a resolved link reaches) and `unresolved` (objects with `target`, `form`, `kind` of `not-found` or `ambiguous`, and `candidates` for an ambiguous link). It reads Markdown links as well as wikilinks and embeds, and resolves each as Obsidian does, against every file in the vault. A template placeholder is in `outgoing` with no `resolved` and is not listed as unresolved. `in` and `both` also return `incoming`: one entry per link to the file, each with `source`, `line`, and `form`, sorted by `source` then `line`. It is read from the link graph after the graph is brought up to date, so a link written outside the server counts, and so does a link from an excluded folder. `in` returns only `incoming`, and `out` never returns it. `in` and `both` fail with `index/disabled` on a vault whose link graph is off, so use `out` there. `incoming` lists every link, so a note that links to the file three times appears three times; use `query_graph` with `backlinks` when you want the linking notes' titles as a graph.

## Finding and listing

- `fs_search_files` matches a case-insensitive glob against each entry's whole path relative to the search directory. A bare `*.md` matches only direct children, so prefix `**/` to match at any depth (`**/*.md`, `**/anti-patterns*`). Use it for names, and use the query tools for content.
- `fs_list_directory` lists one level. Set `with_sizes` to add size and modified time, and `sort_by` (which needs `with_sizes`) to order by name or size.
- `fs_directory_tree` is bounded but can still be large. Set a small `max_depth` and `exclude_patterns`, and scope it to the folder you care about instead of the vault root.
- Listings and searches never show the built-in hidden paths (`.git`, `.contextos`) or anything the operator hid. A direct read of an explicit path is not restricted by that.

## Getting the hash

Overwriting an existing file requires `expected_hash`, the hash of the content you based your change on. It proves nothing has changed underneath you. Writes to a vault are exclusive across every process using it (other agent sessions, ContextOS Web), so the check cannot be raced. Waiting writes are served in the order they arrive, so another session's sustained writes cannot starve yours. If another process is stuck mid-write you get `io/vault-busy` after 30 seconds: retry once, then tell the operator.

- Any read that returns content also returns `content_hash`, except a part of a file (`offset` or `length`), which has none: `fs_read_text_file` (whole, `head`, `tail`, and `range`), `fs_read_multiple_files`, and `frontmatter_read`.
- `fs_attach_file` reports it in the text block after the embedded resource, and that hash matches the content you were given, with no window for the file to change between the read and the hash. It also covers files between the read limit and 10 MiB, which `fs_get_file_info` cannot hash. With `expand_links` it reports no hash at all, so expanded content can never authorise an overwrite.
- If an older server's attachment has no hash block, call `fs_get_file_info`. It does not re-read the content into your context.
- Every successful `fs_write_file` and `fs_edit_file` returns the new `content_hash`. Use that for the next write to the same file instead of reading again.
- The vault stores text with `\n` line endings, as it gives paths with `/`. A text write converts any `\r\n` or lone `\r` it is given, or finds in the file it rewrites, to `\n`, and returns a `write/line-endings-converted` warning; the returned hash is of the converted text. Quote `old_text` for `fs_edit_file` with `\n`, even for a file that still has `\r\n` or `\r` endings. Binary (`content_base64`) writes are stored as given.

## Changing a file

**Small change to an existing file: `fs_edit_file`.** Each edit is an exact `old_text` and `new_text`, and all edits in one call apply together or not at all. That sends only what changed, which is cheaper and safer than resending the file. Group every edit to a file into one call. If you are unsure a match is exact, set `dry_run` to get the unified diff without writing. `expected_hash` is optional here because the exact-match requirement is already a guard, but supply it when your edits rest on an earlier read.

**Whole-file replacement: `fs_write_file`.** Use it to create a file, or to replace one when most of it changes. Provide exactly one of `content` (text) or `content_base64` (binary, up to 10 MiB decoded). A new path needs no hash, and an existing path needs `expected_hash`.

**Conflicts.** A refused write with code `io/conflict` means the file changed after the hash you hold was taken, often because the operator edited it in Obsidian. Re-read the current content, reapply your intent to it, and retry with the new hash. Do not set `force` to get past a conflict, because `force` overwrites whatever is there and can destroy someone else's edit. Use it only when the operator has told you to overwrite.

**Missing parent folders.** Writes and moves create any missing parent folders themselves, so do not create them first. A parent-folder error means the folder could not be created, for example because a file is in the way or permissions forbid it. `fs_create_directory` would fail for the same reason, so report the cause to the operator. Use `fs_create_directory` only when you want an empty directory.

## Moving and deleting

- `fs_move_file` never replaces its destination. Before moving or renaming a note, check what links to it (`query_graph` with `backlinks`), and tell the operator about inbound links rather than assuming they follow the note.
- `fs_delete_file` moves to trash by default, which is recoverable. Pass `hard` only when the operator has asked for permanent deletion, and note that the vault's configuration may still refuse it.
- For several deletions use `paths` (each item succeeds or fails on its own) or a `pattern` with `path` as its base. A pattern matches like `fs_search_files`, so run that search first and confirm the list before deleting.
- `fs_delete_file` also removes empty directories, but not directories that still hold files.
